# Metrics page: live computation over dormant `SprintMetrics` columns

## Status

Accepted — 2026-07-23. Decided while scoping the new workspace **Metrics page**
(`/w/[workspaceSlug]/metrics`), a read-only, cycle-scoped delivery dashboard showing velocity and
merged-PR turnaround. Tickets tracked in Exponential (workspace `syntrofi` / product `exponential`).

**Amended — 2026-07-23 (same day, post-ship).** The original decision computed the page from
`SprintAnalyticsService.getSprintMetrics`, which counts a cycle's **Actions** (the `ActionList`
join, `kanbanStatus === "DONE"`). In production (CLEAR workspace) this returned **all-zeros**: cycle
work is assigned as **Tickets** (`Ticket.cycleId` / `Ticket.status` / `Ticket.points`), not Actions —
CLEAR had 0 Actions in its cycles and 146 tickets across 13 cycles (107 DONE/DEPLOYED). The Metrics
page is therefore **Ticket-based**: velocity/completion/trend compute over the cycle's tickets, with
"completed" = `DONE` or `DEPLOYED`, the completed-ticket **count** as the headline and summed
`Ticket.points` alongside. New service methods `getCycleTicketMetrics` / `getTicketVelocityHistory`
back the UI procedures. The Action-based `getSprintMetrics` / `getVelocityHistory` remain for the
agent-facing `apiKeyMiddleware` procedures **unchanged in this fix** — so the "one service, no drift"
goal below is temporarily unmet on the agent side; realigning the agent onto the Ticket-based path
(or confirming it should stay Action-based) is a tracked follow-up. Everything else below stands:
still live-computed, still no `SprintMetrics` persistence, still merged-PR-turnaround-only.

**Amended — 2026-08-07 (all-cycles roll-up).** The page's headline is now the **all-cycles**
roll-up — every cycle's Ticket metrics summed, with a line chart tracking each metric across
cycles — and the single-cycle view moved below it behind the cycle dropdown. This extends the v1
scope line below ("single workspace-wide roll-up per cycle"); it does not change the decision.
Still live-computed, still Ticket-based, still nothing persisted to `SprintMetrics`. The new
`getAllCyclesMetrics` is **batched** — one query for the cycles, one for all their tickets, one
pass over the workspace's merged PRs — rather than 3N queries, because "recomputing 5–10 cycles is
cheap" stops being true if each cycle costs its own round trips. Cycles with no tickets are
excluded from the series, and a PR falling inside two overlapping cycle windows is counted once in
the roll-up. The bar-list "velocity trend" widget was removed: the chart is a strictly better
version of it. `getVelocityTrend` remains on the router, now unused by the UI.

## Context

The app already has a sprint-analytics backend built for the Mastra PM agent, reached
server-to-server through the `apiKeyMiddleware`-only `sprintAnalytics` tRPC router
(`src/server/api/routers/sprintAnalytics.ts`) over `SprintAnalyticsService`
(`src/server/services/SprintAnalyticsService.ts`). A **Cycle** is a `List` with
`listType = "SPRINT"`, auto-generated by the product plugin's cycle router
(`src/plugins/product/server/routers/cycle.ts`); it reconciles to `ACTIVE`/`COMPLETED` by date.

The schema *anticipates* persisted per-cycle metrics — `model SprintMetrics`
(`prisma/schema.prisma`) has `velocity`, `completionRate`, `avgCycleTime`, `avgLeadTime`,
`avgReviewTime`, `totalPRs`, `avgPrTurnaround`, and `model SprintSnapshot` holds daily counts for
burndown. A future reader will reasonably assume these columns are the source of truth for a
metrics UI. **They are not, and today they are never written:**

- `SprintAnalyticsService.getSprintMetrics(listId)` computes the **active** cycle's numbers **live**
  from the cycle's actions (current `kanbanStatus`, `effortEstimate`) and returns them — it persists
  nothing.
- `getVelocityHistory` **reads stored `SprintMetrics` rows** (`sprint.metrics?.velocity`). No code
  anywhere `create`s/`upsert`s a `SprintMetrics` row, so this method returns all-zeros in practice.
- `avgPrTurnaround` is a column with **no producer** — `getSprintMetrics` never touches
  `GitHubActivity` (the webhook-fed PR/commit event log: `prState`, `prAuthor`, `prMergedAt`,
  `eventTimestamp`), so PR turnaround is computed nowhere.

So two of the page's three metrics (cross-cycle velocity trend, PR turnaround) are not "wire up an
existing endpoint" — they need real computation, and the question is *where the numbers live*.

A bad cached aggregate here is a trust problem, not a data-loss one: if the UI's velocity and the
agent's velocity ever diverged, both would lose credibility. The dataset is workspace-sized —
recomputing 5–10 completed cycles is cheap.

## Decision

- **Compute the Metrics page live, on request. Do not persist `SprintMetrics`, add no cron.**
  - Active cycle: reuse `getSprintMetrics` as-is.
  - Velocity trend: **rewrite `getVelocityHistory`** to recompute each recent *completed* cycle the
    same way the active one is computed. A completed cycle's actions' final `kanbanStatus` is stable,
    so a live recompute is accurate and needs no stored row.
  - PR turnaround: **new** live aggregation over `GitHubActivity` — join each PR's `opened`-event
    `eventTimestamp` to its `prMergedAt`, averaged over PRs merged within the cycle window.
- **Velocity is reported as both a count and points.** Completed-action **count** is the headline
  (robust when `effortEstimate` is unset); summed `effortEstimate` shows alongside. (The existing
  service already sets `velocity = completedEffort`, i.e. points; the count is `completedActions`.)
- **`SprintMetrics.velocity` / `avgPrTurnaround` / `avgCycleTime` / … stay dormant in v1.** They are
  left in place as the natural home for a *future* persist-on-completion caching layer, but nothing
  reads or writes them for this page.
- **UI auth is additive.** Add `protectedProcedure` + `assertWorkspaceMember` variants to
  `sprintAnalytics` for the page; the `apiKeyMiddleware` procedures the agent uses are untouched, so
  humans and the agent read through **one** service and cannot drift.
- **Scope of v1:** single workspace-wide roll-up per cycle (no per-project/per-person slicing);
  merged-PR turnaround only (no live open-PR-age panel); nav item "Metrics" in the "Deliver" section,
  `requiresPlugin: 'product'`.

## Consequences

- No staleness, no backfill, no scheduled job; the page is always internally consistent with the
  agent's view.
- If live recompute ever gets heavy, the fix is to **populate the already-existing `SprintMetrics`
  columns on cycle completion and read them** — a caching optimization, not a redesign. This ADR is
  the record that those columns are deliberately dormant, not forgotten.
- Historical velocity reflects each cycle's actions' *current* final state, not a frozen snapshot —
  if a long-closed cycle's actions are later edited, its historical number shifts. Accepted for v1
  (closed-cycle actions are effectively immutable in practice).
